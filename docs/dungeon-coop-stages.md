# 多人副本：第 0～2 階段（房間、公開招募、好友邀請）

本階段提供獨立的副本隊伍服務與好友邀請通知。**第 3 階段才新增正式組隊、準備及出發介面**；目前尚無副本地圖、即時戰鬥、獎勵或啟動副本指令。

- 驗證：所有 `POST /api/dungeon/room` 動作使用主帳號 Firebase A 的登入票證，副本房間資料存在 Firebase C，與舊 `raidRooms`、`tacticalBattleRooms` 分離。
- 私人房間：`create`（預設私人）／`join-code`／`get`／`reconnect`／`leave`，六碼房碼只有隊員才看得到。
- 公開招募：`create` 可指定 `visibility:"public"`；`set-visibility` 僅房主可切換；`list-public` 只呈現未過期、尚未滿四人、有效房主仍在隊伍內的等待中公開房間。公開資料不包含房碼、UID 或隊員詳細資料。
- 公開加入：`join-public` 透過房間 ID 入隊，交易內再次檢查公開狀態、剩餘名額與過期時間。即使知道私人房間 ID 也不能藉此加入。
- 快速組隊：`quick` 優先加入人數較多的公開隊伍；無可加入隊伍則建立公開房。已在有效隊伍中的玩家直接返回原房間（不擅自公開私人房）。
- 好友邀請：`inviteDungeonFriends(room, friendUids)` 使用現有 `/api/invitations/send`，伺服器重新驗證邀請者為目前有效房主、房碼正確、房間尚有名額，只向已確認為好友的接收者推送；接受時呼叫 `join-code` 再次驗證。舊主頁邀請通知已支援「合作副本邀請」與加入事件。
- 伺服器的好友通知沿用既有短時佇列（目前 2 分鐘），跨多個 Render instance 的長期可靠通知與正式房間即時同步仍屬後續第 4 階段。
- 預留 `ready` 欄位但不啟用 `start`；第 3 階段新增正式遊戲內隊伍、準備介面，第 4 階段新增持續同步。
- 副本不消耗舊團本入場券，不寫入舊戰場紀錄，也不發放獎勵。

驗收：`node --test tests/dungeon-room-api.test.cjs tests/dungeon-public-recruitment.test.cjs tests/dungeon-friend-invitations.test.cjs`、`npm test`、`npm run check:module-versions`。

## 第 3 階段：集結與隊長管理

- 已加入 `ready`、`kick`、`disband`、`start`、`cancel-start` 的伺服器權威操作。僅隊員可以準備；踢人、解散及集結／取消集結僅隊長操作。相同準備值、重複開始與取消不重複增加版本。
- `start` 會在全隊準備後，將房間狀態從 `waiting` 轉為 `assembled`。這只是**集結完成**，不代表已進入未實作的探索地圖；可由隊長 `cancel-start` 回到等待室，重新要求全員準備。集結中不接受新玩家加入。
- 隊員在集結中仍可離開，剩餘隊伍重回等待室；隊長離開則轉交新隊長。解散房間在交易內撤銷各成員指向該房間的索引，並關閉房碼。
- 隊員的境界／修為由伺服器主專案可信快照推算，不依賴前端提供。
- 前端新 `public/cultivation/dungeon-lobby.js` 提供宗門「合作副本」入口、獨立集結畫面、隊員資訊與準備狀態、隊長管理、六碼複製與好友邀請、公開列表與快速組隊。暫以五秒間隔同步已開啟的等待室；第四階段會接正式即時串流。
- 額外修正既有問道試煉 Canvas 的長按原生選取／藍色反白及 iOS callout；`touch-action:none` 只限制戰場互動區域，問答文字及輸入框仍可正常選取。

## 第 4 階段：可靠的跨裝置即時同步與在線狀態

- `POST /api/dungeon/room` 新增 `subscribe`（帶 Firebase A 授權標頭的 SSE 長連線）及 `heartbeat`（僅隊員可回報）。`dungeon-room-stream.cjs` 使用 Firebase C `onSnapshot` 觀察權威房間文件，支援不同 Render 執行個體／不同裝置共同接收狀態；不依賴單一 Node 進程記憶體。
- 初次訂閱先驗證隊員及未過期狀態，再傳送經過同一 `publicRoom` 投影的資料。串流以遞增 `revision` 去重；被踢、房間關閉或過期立即回傳 403／410 並終止，防止已失去資格的玩家繼續讀取。
- 房間串流每 15 秒發 keepalive、最高 1 MB 等候寫入、每 4 分鐘關閉重新驗證 Firebase A token；斷線由客戶端以退避重新連接。房間狀態透過 HTTPS POST，不把登入憑證放到 URL 或本地儲存。
- 心跳約每 20 秒送出，伺服器設 12 秒最小寫入間隔。由伺服器記錄 `heartbeatAtMs`，超過 60 秒無更新在介面顯示「離線」，但**不因暫時離線把玩家踢出或清除準備狀態**。
- 當已建立的隊伍剩餘存活時間低於 30 分鐘，心跳在同一 Firestore 交易續期房間及六碼房碼至兩小時（先確認代碼仍屬於這個房間）。
- 前端以串流為優先，不再在正常連線時每五秒讀取房間。離線時才使用有退避的驗證 GET 補查；隱藏／離開頁面會關閉串流，重新回到頁面會重新建立訂閱。
- 每個回應只可更新自己已加入的房間；用 `revision` 擋掉落後的 HTTP 回覆與過期串流封包，不讓舊準備狀態蓋掉新的狀態。切換帳號或退出畫面關閉訂閱。
- 介面顯示「即時同步／重新連線中」及各隊員「在線／離線」，長時間無心跳只影響顯示，不影響誰能操作；先前階段的私人／公開／隊長權限維持由伺服器決定。
- **本階段仍未開放副本地圖或戰鬥**。伺服器 `start` 只代表集結完成的 `assembled` 狀態，將於下一批地圖階段接入實際進場。

測試：`node --test tests/dungeon-*.test.cjs`、`npm test`、`npm run check:module-versions`。

## 第 5 階段：種子碼副本地圖 v1（生成與驗證）

此階段僅交付**伺服器權威地圖資料**，第 6 階段才加入 Canvas 地圖檢視與拖移縮放，第 7 階段再加入玩家移動及障礙碰撞。**目前按下「確認集結出發」仍僅進入 assembled 隊伍狀態，沒有啟用戰鬥或獎勵。**

### 地圖與資料契約

- 純演算法 `dungeon-map-generator.cjs`：`generateDungeonLayout(seed)` 產生 `layoutVersion:1` 的可重現地圖；在 Node.js 與不同 Render instance 上同種子必然得到相同的 JSON。禁止修改 v1 的已發布生成規則；未來新增變化應開新版本。
- 建立副本房間時由**伺服器**產生密碼學隨機的 24 碼十六進位 `mapSeed`，與 `mapVersion` 一起持久化於 Firebase C `dungeonRooms`。玩家不能指定／覆寫種子。邀請碼與地圖種子碼互相獨立。
- `POST /api/dungeon/room` 的 `get-map`（body 僅需要 `roomId`），必須使用 Firebase A 登入 Token，且需要實際在該個未關閉、未過期的房間中。當玩家被踢、退出、房間解散或逾時，均不再開放讀取。
- 此路徑不寫入地圖文件，也不消耗舊團本票券、體力或獎勵。多人玩家、斷線重連與不同後端 instance 可透過儲存的 `mapSeed` 重新取得完全一致的藍圖；舊版本已建立、沒有 `mapSeed` 的等待中房間以 `legacy:<roomId>` 派生固定種子，毋須遷移資料。
- `publicRoom`／SSE 房間快照與公開招募列表**不透露** `mapSeed`；地圖內容只在隊員授權讀取時傳回。前端 `getDungeonMap(roomId)` 對應此 API，未在瀏覽器自行產生或覆寫地圖。
- 地圖 `tiles` 為 row-major 長度 `width*height`：`0` 為不可通行牆面、`1` 為通道地面、`2` 為較開闊的地面；地圖四周必為牆，所有可通行格構成**同一個 4-方向連通分量**。
- 11～12 × 9～10 個邏輯地格經放大形成約 **47～51 × 39～43** 的實際格網。生成器以隨機化深度優先迷宮樹抽取**非自交、蜿蜒主路線**（至少 5 個轉彎），另添 **2～4 條實際接通且有盡頭的支線**，預留不規則空地與至少 2 格寬的通道。
- 地圖包含 `spawn`、四個不同的 `spawnPads`、`mainRoute`、`branches[]`（`entrance`／`end`／`route`）、`deepest`、`guardianSite`、`portalSite`、`biome` 與 `layoutId`。`guardianSite` 位在主線最深端，支線出口不會比它更深；`portalSite` 在最深端前方四格，供後續階段使用。
- 四種地貌名稱：青竹幽徑／殘碑古道／霜嶺石窟／雲隱荒澤。現階段是**生成資料與地貌主題**，不是已完成美術或遊戲場景。

### 驗收

- `tests/dungeon-map-generator.test.cjs`：1,200 個種子碼的決定性、支線數量、轉彎數、牆邊界、主支線逐格連通、四人出生點、唯一連通分量、支線深度、地貌多樣性及不可變版本。
- `tests/dungeon-map-api.test.cjs`：伺服器種子保存、請求端不能自訂種子、四名隊員／兩個 server instance 的地圖完全相同、未授權拒絕、集結後不更動、解散後不可讀、舊房間無種子時的穩定 fallback。
- 專用 CI `Dungeon co-op synchronization acceptance` 會一併檢查 `dungeon-map-generator.cjs` 語法並執行所有 `tests/dungeon-*.test.cjs`。

## 第 6 階段：副本地圖視覺與鏡頭（預覽模式）

- 繼續使用第 5 階段的同一個 `get-map` 授權 API；前端不自行產生地圖、不儲存種子、不改寫房間或玩家位置。
- 宗門「合作副本」等待室新增「檢視地圖」按鈕，隊伍集結完成時會在各隊員已開啟的組隊介面自動進入讀取地圖的展示頁。重新連線時若房間仍為 `assembled` 也能恢復預覽；玩家關閉預覽後不會被同一狀態連續強制彈回。
- `dungeon-map-camera.js` 提供視窗符合比例的相機，支援滑鼠滾輪／觸控雙指縮放（`1～6×`）、單指與滑鼠拖曳、按鈕縮放、全圖、定位四個預留出生點、方向鍵與橫直式／視窗尺寸變換。Zoom 使用指標座標錨點，地圖不允許完全滑出畫面。
- `dungeon-map-painter.js` 使用既有 `tiles` 地圖資料繪製通道、岩壁、空地紋理、四種色調不同的地貌，並標註出生點、守護者、傳送陣及四個隊員預留位置；路線提示可由使用者開關。右上角縮圖會顯示鏡頭在整張地圖中的位置。
- `dungeon-map-view.js` 是獨立的全畫面展示視窗，包含可點擊的地圖控制、鍵盤替代操作、有效隊員身分檢查、尺寸觀測與載入錯誤重試。地圖呈現透過 `requestAnimationFrame` 排程，不重複建立永久動畫迴圈；關閉時清理動畫、觀察器與操作狀態。手機地圖 Canvas 停用系統長按反白，不影響答題輸入。
- **本階段是「地圖預覽」，並沒有開始探索、移動、靈獸、獎勵或角色同步。** 第七階段才把四名玩家的伺服器權威位置與體力及碰撞接上，此時定位只跟隨玩家的*預留出生點*，不是假裝玩家已經移動。
- `tests/dungeon-map-camera.test.cjs` 對不同螢幕比例、縮放與視角限制、resize 和 map 不可變性進行檢查；`tests/dungeon-map-view.test.cjs` 對四種地貌、縮圖及功能接線進行測試。

## 第 7 階段：伺服器權威的多人步進探索

本階段將第六階段的地圖預覽接上**實際四人獨立移動**。仍沿用集結後的 `status: assembled`，不提前新增尚未完成的敵人 AI、攻擊、答題充能或獎勵。

### 狀態與移動權限

- `start` 通過全隊準備驗證後，在**同一個 Firebase C 交易**中，按加入順序把四位隊員放到各自的 `map.spawnPads`，設定每人 `position:{x,y}`、`explorationStamina:100`、`moveSeq:0`；也支援舊房間沒有地圖種子碼的固定版型。
- 只有 `assembled` 狀態下、真實登入的隊員才可呼叫 `POST /api/dungeon/room` 的 `action:"move"`，提供 `roomId`、`dx`、`dy`、`step`。`dx,dy` 必須是整數且 `|dx|+|dy|=1`（上下左右一格）；不接受由瀏覽器提供終點、位置或剩餘體力。
- `dungeon-movement.cjs` 使用**伺服器保存的地圖種子碼**再生同一張地圖，逐步核對位置與地圖 `tiles`，拒絕斜走、瞬移、出界與撞牆。通行的每一格消耗 **1 點副本探索體力**；撞牆或錯誤請求不扣體力也不改寫房間。
- `moveSeq` 由每位玩家各自遞增，Firestore 交易驗證 `step===moveSeq+1` 才能接受；同一個上一筆指令若完全相同可重送且**不再扣體力**，過時／跳號／不同方向的指令會拒絕。不同裝置、不同 Render 執行個體同時發送，也只能以成功交易的結果為準。
- 玩家彼此**不會阻擋通道**：允許共同站在同一個格子，Canvas 會把重疊的隊員圖示稍微錯開，避免合作副本中的卡位或阻擋。每人的位置、體力與 `moveSeq` 相互獨立。
- 每個成功移動更新房間 `revision` 和該隊員的資料，經第四階段 Firestore `onSnapshot` SSE 即時同步到其他隊員。斷線重連可以從伺服器恢復當前位置及探索體力，前端只送方向指令，不樂觀修改地圖狀態。
- 若隊伍尚未完成集結、房間過期、玩家已被踢／離開、體力耗盡或撞牆，伺服器會回覆錯誤且不移動。已有人成功走出第一步時不允許隊長單純「取消集結」，避免進度被隱性倒帶；隊員仍可退出，剩下的人返回等待室並在再次集結時開始新的探索。
- 本階段的 **100 點探索體力是暫定副本專用值**，並非玩家原有一般體力、舊團本票券或問道試煉的能量，也不會寫入主玩家帳戶。答題補充探索體力將在後續的「獨立答題與充能」階段接入，現階段耗盡時會停止移動，不會假裝能充能。

### 介面

- `dungeon-map-view.js` 加入手機／平板的四方向按鈕、`W/A/S/D` 鍵盤步進控制，以及目前探索體力／格子位置 HUD。方向鍵仍可平移視角；地圖仍支援原本的拖曳、雙指縮放、定位、路線切換與全域縮圖。
- 成功第一步後預設放大並跟隨自己的**實際伺服器位置**；觸控拖曳和滾輪操作鏡頭仍不消耗探索體力。地圖及縮圖上的隊友標記使用同一份 Firebase 房間狀態，每人可以獨立移動。
- 玩家點擊移動後在伺服器確認前停用重複操作。409 錯誤會重新讀取權威房間，避免同一個玩家在不同裝置上使用舊 `moveSeq`；房間更新會依前一階段的單調 `revision` 規則，回饋給等待室與地圖。
- 集結後等待室顯示「進入探索」，不再宣稱無法移動；任何人成功移動後，不再顯示可取消探索的按鈕（只有完成集結但尚未有人走動時可返回等待室）。

### 驗證

- `tests/dungeon-movement.test.cjs`：檢查一千兩百張地圖上的四人出生點、上下左右移動、重複封包、撞牆、不合法座標／序號與體力耗盡。
- `tests/dungeon-room-movement.test.cjs`：檢查多人在兩個伺服器執行個體上的位置／體力一致性、獨立併發、斷線重連、不扣舊團本票券、離開與過期權限。
- `scripts/test-dungeon-map-browser.cjs`：保留兩個 Chromium 頁面模擬雙玩家進房、集結、觸控縮放及手機桌面版型，新增雙方可獨立移動且各扣一格的行為驗收。
- 專項自動測試命令：`node --test tests/dungeon-*.test.cjs` 與 `npm run check:module-versions`。 

## 第 8 階段：伺服器權威即時戰場時鐘

### 時間資料與交易一致性

- `dungeon-battle-clock.cjs` 定義不可變版號 `CLOCK_VERSION=1` 及 `TICK_MS=1000`。**不使用玩家端時鐘計算戰鬥結果**。隊長集結成功時，在保存四個出生點的同一 Firebase C 交易中寫入 `battleStartedAtMs`（伺服器時戳）、`battleAppliedTick=0`、`battleAppliedAtMs` 及版本。
- 所有隊員看見的 `room.battleClock` 由 `publicRoom` 按同一個起始時間及**回應端當前伺服器時間**計算，包含 `version`、`tickMs`、`startedAtMs`、`serverNowMs`、`elapsedMs`、`tick`、`appliedTick` 及 `nextTickAtMs`。等待室與已關閉的房間不回傳進行中的時鐘。
- `elapsedMs` 與當前邏輯 `tick` 由已過的實際伺服器時間推導；即使所有玩家暫時離開畫面或 Render instance 重新啟動，也**不重置或暫停**。玩家回來後無須以客戶端補送舊的每一秒；伺服器根據起點計算當前 tick 並恢復。
- `battleAppliedTick` 為**已提交的節拍游標**，和即時計算的 `tick` 分開。簽名 `POST /api/dungeon/room` 的 `action:"clock"` 會在同一 Firestore 交易檢查房間仍有效且使用者仍為隊員，僅於 tick 增加時提交 `battleAppliedTick`、`battleAppliedAtMs` 和 `revision`。同一 tick 在多台伺服器競爭時只會提交一次，沒有新 tick 不寫入；任何客戶端提供的時間、tick、暫停參數皆忽略。
- `subscribe` SSE 連線在集結中每秒由伺服器觸發一次有節流的 transaction 嘗試；透過 Firebase C `onSnapshot` 將新 revision 傳給所有裝置；停止訂閱／斷線／房間失效便清理 timer。當沒有任何連線時，不進行無謂的每秒資料庫寫入，但邏輯時鐘仍依伺服器時間推進；重新訂閱、移動、心跳或 `clock` 請求都能追上已過秒數。
- 移動和心跳會在既有 Firestore 寫入交易內同步補上應有的 tick，避免玩家無法訂閱時先移動而時鐘落後。多人位置、體力、題目資料、入場票券不被時鐘修改。原有 `get`／`reconnect` 只用權威時間顯示，不額外收費或強迫寫入。
- 舊的已集結房間若沒有 `battleStartedAtMs`，使用既有 `assembledAtMs` 作為穩定的起點，不強制遷移；取消集結並重新集結時才開啟新時鐘。計時與線上心跳不同：玩家離線不會讓戰場暫停。

### 玩家畫面與後續承接

- `dungeon-map-view.js` 的上方 HUD 顯示 `戰場時鐘 mm:ss · Tn`。畫面每 250 毫秒更新文字，僅用 `performance.now()` 推估兩次伺服器快照間的視覺秒數，**不把瀏覽器時間寫回伺服器**。切換視窗、鏡頭拖曳、移動、打字或關閉地圖不影響伺服器時鐘；SSE 重連會依新的伺服器資料重新校準。關閉地圖清除專屬 timer。
- 本階段**尚未新增靈獸 AI、傷害／攻擊、答題充能**。第 9 階段才讓敵人的位置及行動與 `battleAppliedTick` 共同納入伺服器交易；有客戶端連線時自動推進，無客戶端連線時的歷史 tick 將由未來 AI 模組決定如何補跑。此階段只負責可靠的時間、權限、事件發送及顯示，不偽稱 NPC 已自行活動。
- 專項測試 `tests/dungeon-battle-clock.test.cjs`、`tests/dungeon-battle-clock-api.test.cjs`、`tests/dungeon-clock-stream.test.cjs` 驗證時間計算、舊房間、伺服器爭用、重連補時、取消集結及 SSE 資源清理；雙玩家 Chromium 測試加入雙方時鐘在**無移動時也會前進**且同一節拍附近同步的驗收。

## 第 9 階段：伺服器權威靈獸巡邏與追蹤（不含攻擊）

### 行為與資料契約

- 新增 `dungeon-enemy-ai.cjs`，僅由後端操作靈獸。集結交易使用**伺服器保存的地圖種子**，每條支線配置一隻靈獸，另於主路線配置兩隻，合計 **4～6 隻**。命名與種類：巡山妖狼（每 2 秒／Tick 週期 2）、迷霧靈狐（每 3 秒／Tick 週期 3）、岩甲巨蜥（每 3 秒／Tick 週期 3）。
- 靈獸固定 `id`、`kind`、`name`、`zone`、`spawn`、`position`、`cadence`、`aggroRange`、`patrolIndex`、`patrolDirection`、`intent`、`targetUid`、`lastActionTick` 持久化於**同一份 Firebase C dungeonRooms 房間文件**。集結時與四人出生點、初始戰場時鐘一起提交；舊階段已集結且尚無靈獸的房間，在下一次有效 Tick 交易按原地圖種子補建。
- 靈獸依伺服器戰場時鐘（第八階段）自主行動。玩家**不需移動或按任何按鈕**，連線中的 SSE 每秒觸發伺服器校驗，Firestore 交易只會讓每個 Tick 的靈獸狀態提交一次，不受 Render 多個 instance／多位玩家同時訂閱的影響。
- 每隻靈獸沿區域內主線或支線往返巡邏；感應半徑依種類約 6～10 格。感應到玩家後使用**四方向 BFS**，尋找通行的最短路徑；距離玩家一格時切為警戒並停下，**不踏入玩家格、不穿牆、不斜走、不瞬移**。失去目標後沿可通行地格返回巡邏路線。多隻靈獸不會佔據相同格子，受阻時也不會跳過巡邏路點。
- 靈獸只會移動及標記「巡邏／追蹤／警戒／返回」狀態，**第九階段不啟用靈獸攻擊、傷害、死亡、生命值減少、掉落、經驗值或其他獎勵**。原有單人戰棋、舊團本、主角色資料及原有答題系統皆不受更動。
- 一旦發生伺服器 Tick、合法玩家移動或既有心跳寫入，均會在房間交易內合併 `battleAppliedTick`、`enemies`、`enemyAiVersion` 和 `revision`。客戶端不接受或寫入敵人位置、AI 版本、Tick、偵測範圍、方向或攻擊效果；伺服器只依自己的地圖資料和可信隊員位置判斷。
- 無隊員保持串流時，不進行逐秒的無意義資料庫寫入；下次有人恢復連線，伺服器會追上**當前時間 Tick**，但最多模擬最後 **24 個 Tick** 的敵人行動。這是**離線追時的有界簡化**：不回溯重演整段無玩家的歷史戰鬥，也不補發任何傷害。避免兩小時離線後造成大量 Firestore 計算／回溯攻擊。
- `publicRoom` 隊員快照傳送 `enemyAiVersion` 和經篩選的 `enemies`（名稱、種類、目前座標、狀態與最近行動 Tick）；**不包含地圖密碼種子及 AI 巡邏路線／方向內部狀態**。非隊員、過期房間及已解散房間不能讀取。
- 全員取消集結或成員離開導致回到等待室時，清除敵人、戰場時鐘及先前探索位置；隊長解散亦清除戰場資料。重新集結會從相同種子建立初始部署，不沿用上次探索進度。

### 玩家地圖

- `dungeon-map-painter.js` 使用伺服器回傳的靈獸 `position` 繪製三種不同顏色／符號的靈獸標記；處於追蹤／警戒狀態時加強顯示紅色外圈。隊員圖示始終繪製在靈獸圖示上層，不會被靈獸的攻擊範圍或其他遮罩蓋住。縮圖亦顯示隊伍與靈獸即時位置。
- `dungeon-map-view.js` 增設「靈獸 N」控制及可收合的動向面板，可查看每隻靈獸的名稱、行為狀態、座標、行動週期和最近 Tick；點選清單可定位並跟隨靈獸，點擊地圖上的靈獸或在手機**長按約 480 ms**亦可打開詳細資訊。鏡頭拖曳／雙指操作與靈獸檢視彼此分離，不會誤當成移動命令；地圖 Canvas 仍禁用手機長按藍色文字反白，資料面板文字可正常閱讀。
- 畫面由多人房間 SSE 更新，重連後不依賴客戶端本地 AI 重新預測位置；實際同步品質受 Firestore 及網路延遲影響，並非補間至逐影格的動畫。下一階段再加入更多 AI 決策與戰場效果。

### 驗收

- `tests/dungeon-enemy-ai.test.cjs`：1200 個種子、4～6 隻不重疊且可通行出生點、BFS 逐格路徑、仇恨半徑、巡邏受阻、不入玩家格、獨立週期、24 Tick 有界追時、不修改玩家體力或地圖。
- `tests/dungeon-enemy-ai-api.test.cjs`：兩個伺服器實例於同一 Tick 合併成一次交易、移動與靈獸時鐘同步、篡改請求被忽略、非隊員權限、重組重置、舊房間補建。
- `tests/dungeon-enemy-view.test.cjs`：Canvas／縮圖靈獸繪製、點選與長按、雙指操作防誤觸、文字反白防護、前端不直接改寫 AI 狀態。
- Chromium 雙玩家瀏覽器驗收：不移動也有靈獸巡邏，兩位玩家都能看到靈獸清單與更新的行動資訊，既有手機／電腦操作與玩家移動繼續有效。

## 第 10 階段：預警攻擊、走位閃避與副本獨立生命值

本階段為副本的第一批**真實傷害判定**：保留第 9 階段的自主巡邏和尋路，在發現玩家且攻擊路徑有效時，先公佈紅色危險格再結算命中。玩家仍只能移動，尚未啟用角色攻擊、擊殺、獎勵、答題補體力、治療或救援，避免將舊單人問道試煉的系統誤接到合作副本。

### 伺服器資料與規則

- `dungeon-enemy-combat.cjs` 定義純後端攻擊幾何與結算：**巡山妖狼「撕咬突襲」8 點**（相鄰單格）、**迷霧靈狐「靈焰直射」6 點**（前方直線最多 2 格）、**岩甲巨蜥「震地扇擊」12 點**（前方一格，延伸前方第二列扇形最多 4 格）。所有攻擊格由伺服器保存的種子地圖檢查是否可通行，直線不得穿牆。
- 靈獸只有在其合法行動 Tick 才能對活著、位置有效的隊員選擇目標，先在 Firebase C 房間中持久化 `attack:{kind,label,damage,from,cells,startedAtTick,resolvesAtTick,targetUid}`；`resolvesAtTick=startedAtTick+2`，因此至少有兩個戰場節拍的預告。攻擊預告時靈獸不瞬移追擊，玩家有時間走位。
- 命中時再次用**當前的伺服器玩家位置**比對原本公布的危險格；走出警告區就不受傷。同一格的多名活著玩家可同時受擊，同一隻靈獸在同一次結算對每位玩家最多扣一次生命。命中／落空均記錄 `lastAttack` 與結算 Tick。傷害完全由伺服器交易執行，不能由玩家端偽造時間、傷害量、敵人位置或目標。
- 集結時每位玩家獲得**100 點副本專用生命**（`battleHealth`、`battleMaxHealth`、`downed:false`、`lastDamage:null`），與原有探索體力（100）、角色修為、原有戰棋生命、團本票券完全分離。戰鬥血量降至 0 時設定 `downed:true`，停止移動並停止被 AI 當作可追蹤目標，不產生負血。**本階段尚無復活／治療**；日後的救援階段再加入。
- `battleAppliedTick` 仍是唯一的伺服器權威節拍游標，與靈獸 `attack`、`lastAttack`、全員 `battleHealth`、`downed`、`lastDamage`、房間 `revision` 一起進入同一筆 Firestore 交易。不同執行個體、四名隊員的 SSE、移動／心跳／時鐘請求即使同時抵達，成功提交的同一 Tick 只計算一次傷害，回傳的房間快照同步給所有隊友。
- `heartbeat` 先合併 AI 傷害後再寫入自己的上線時間，避免以舊的玩家物件覆蓋最新扣血；移動端只接受四方向單步指令，不接受健康或體力覆寫。玩家不能走進目前靈獸佔據的格子；已倒地玩家無法移動。
- 若伺服器超過 **3 個 Tick 未成功寫入戰場狀態**（例如整隊離線／休眠），回來時最多補模擬最後 24 Tick 的**純移動**；會取消舊的未結算攻擊，至當前 Tick 重新生成新預告，不會把沒機會看見的歷史預警一次性結算成傷害。此保護是為了公平：長時間離線的玩家不會上線瞬間倒地。
- 取消集結、成員離開導致返回等待室、或解散房間時，刪除前一場探索的副本血量與傷害、敵人與時鐘資料。再集結才有新的完整生命；不允許在舊場景直接保留傷害／擊殺狀態。

### 玩家視覺與互動

- `dungeon-map-painter.js` 在**玩家與靈獸圖示的下層**繪製紅色半透明危險格與明亮外框；圖示不會被預警攻擊範圍蓋住。縮圖同步顯示危險區；所有隊員標記可顯示副本血量條和近期傷害 `-N`。
- `dungeon-map-view.js` 顯示自己的 `生命 N/100`、接近歸零的警戒顏色、腳下受到攻擊鎖定時的預告倒數，以及全隊 HP／倒地概況。靈獸資訊面板增加「準備攻擊／收招中」與預告名稱、結算 Tick／最近命中人數。
- 撞牆、躲避、離開警告格時仍只有**合法移動**會消耗 1 點探索體力；危險區本身不直接扣體力。玩家倒地後方向鍵停用並顯示等待後續救援，避免誤以為攻擊無效或網路延遲。
- 玩家可點選或長按靈獸檢視；Canvas 保持手機長按反白防護，面板文字仍可閱讀，鏡頭拖曳、縮放、紅格預告均不觸發任何客戶端攻擊結算。

### 驗收項目

- `tests/dungeon-enemy-combat.test.cjs`：三種攻擊幾何、牆面限制、T+2 預告與一次命中、移開閃避、多人同格傷害、倒地禁止移動、離線補時不傷害、純函數可重現。
- `tests/dungeon-enemy-combat-api.test.cjs`：真正伺服器組隊／集結、篡改參數無效、兩台後端同時時鐘／心跳無重複扣血、走位閃避、倒地拒絕步進、訪客無法查看、解散清空戰場。
- `scripts/test-dungeon-map-browser.cjs`：兩位不同視窗的玩家親自經歷「出現紅色危險提示 → 伺服器命中扣血 → 隊友 HUD 同步血量」，並保留第 6～9 階段的地圖操作與靈獸自動移動驗收。
- 專項測試：`node --test tests/dungeon-*.test.cjs`；全專案回歸、`npm run check:module-versions` 與 Chromium 瀏覽器驗收由 GitHub Actions 執行。

## 第 11 階段 A：多人即時近戰基礎（已實作，尚非完整功法技能）

- 新增獨立 `dungeon-player-combat.cjs`：當玩家在靈獸上下左右相鄰格時可隨時出拳攻擊，每次耗 2 點**副本探索體力**、固定造成 30 點初版測試傷害。這是測試用近戰基礎，**不是**現有六套功法技能的最終傷害公式。沒有回合限制或冷卻，不會碰觸舊問道試煉及舊團本。
- 三種靈獸初始獨立生命分別為：巡山妖狼 60、迷霧靈狐 60、岩甲巨蜥 90。只從伺服器種子地圖產生，攻擊範圍、耗體與扣血均由伺服器檢查。生命歸零時在同一 Firebase C 交易中移出敵人清單，避免已死靈獸繼續追擊或攻擊。
- `POST /api/dungeon/room` 新增 `action:"strike"`，只收 `roomId`、`enemyId`、個人單調遞增 `seq`。相同已提交攻擊重送不會再次扣血、扣體力或遞增 revision；不同玩家同時出手使用 Firestore 交易串列化，不會遺失傷害。重連後由共享快照接續個人序號。
- 地圖選取靈獸後，在相鄰一格時解鎖「攻擊」按鈕；不符合距離、倒地或體力不足即停用。伺服器回報命中傷害、剩餘血量或擊敗，並向全隊即時推送靈獸血條及消失狀態。手機仍可用原先的點選／長按靈獸方式指定目標。
- 不發放掉落、密鑰、經驗或獎勵，也不修改主角色能力值。第 11 階段 B 將接入已裝備功法的實際技能、射程、範圍、多段傷害與戰中配置切換；第 12 階段才整合獨立答題補體力。本階段的 100 點起始探索體力仍為臨時測試值。
- 自動化：`tests/dungeon-player-combat.test.cjs`、`tests/dungeon-player-combat-api.test.cjs` 驗證純函數、身份驗證、跨兩個 Render instance 的多人同時攻擊、防偽造、倒地及防重送；`scripts/test-dungeon-map-browser.cjs` 新增瀏覽器對兩次攻擊、共享擊殺與雙人同步的驗收。


## 第 11 階段 B：可裝備功法的即時戰鬥（多人共用）

### 權限與資料來源

- 集結前先從 Firebase A 可信讀取每位玩家的 `tacticalManuals`，核對隊伍名單沒有變動，再在 Firebase C 房間交易內一次寫入已裝備功法，從原本的六本功法、EXP、技能升級與三組預存配置建立副本專用戰鬥資料。未取得功法或未裝備技能的修士保留第 11A 的普通攻擊；只要目前配置有技能就以技能取代普通攻擊，與既有問道試煉一致。
- 由於玩家功法在 Firebase A、副本隊伍在 Firebase C，兩者不能進行跨資料庫原子交易：每次施放／切換都先從 A 讀取伺服器可信快照，再由 C 的單一房間交易檢查版本和提交全部戰鬥效果；若隊伍名單在集結前後變動，直接拒絕過期的出發請求。
- 伺服器在施法時重新讀取目前的功法紀錄，檢查真正持有、熟練 Lv.5/Lv.10 解鎖、境界門檻及副本內**目前裝備**的技能。瀏覽器無法指定/竄改技能升級、基礎攻擊、最終傷害、耗體、NPC 生命或角色位置。
- 新增獨立 `dungeon-skill-combat.cjs`，不更動一般 `tactical-rules.js` 及原本功法存檔。副本專用傷害尺度為 `30 + min(200, 目前已擁有功法的等級合計)`，乘上技能升級後的倍率；這不是舊問道試煉的最終戰鬥攻擊值，仍需於副本平衡階段驗證。
- `action:"skill"` 只接受 `roomId`、`skillId`、`target:{x,y}`、個人嚴格遞增 `seq`。`action:"loadout"` 只接受 `roomId`、三組之一的 `index`；切換不扣體力，不使用回合數或冷卻。敵人結算、角色位置與技能效果和 `revision` 均在同一 Firestore transaction 寫入，同一有效操作重送不再次扣費或造成傷害。
- 為避免同步與重複處理問題，玩家基礎普通攻擊及功法各有獨立操作序號；同時更換配置與施法，仍以先成功提交的房間交易為準。

### 目前已接入的功法動作

- 流風斬、直拳、遠線破擊：依方向發出穿行直線的劍氣／拳勁；範圍由原有功法資料決定，無法穿牆，遠線破擊有可通行的擊退效果。
- 突進橫斬、突進震拳、踏步連拳：必須選擇可抵達的空白直線地格，伺服器先檢查路徑，落點前方進行範圍攻擊／雙段傷害。
- 交叉劍斬、八方合劍：攻擊中心及周圍的交叉／八向劍氣，不穿過地形；中心僅計入實際可形成的劍氣交會。
- 召劍：第一次在可到達空格召出個人飛劍，不造成傷害；之後沿直線移動飛劍，對穿過的靈獸造成傷害。與其他隊員的飛劍資料相互獨立。
- 崩山拳、四步連推、翻摔：支援扇／T 型範圍、逐段推進和撞壁傷害、摔至身後可通行空格。防止推入牆壁、其他靈獸及玩家；位移中的預告攻擊會取消。
- 蓄勢：副本中獲得六層效果，已在此階段預先接入；每次成功施放一個技能消耗一層，體修非蓄勢技能耗體減半向上取整，多段命中只扣一層。蓄勢本身重置為六層，不算其中一次。後續第 13 階段仍應完整驗證數值平衡與多裝置連續操作。

### 戰場操作與品質邊界

- 戰場左側增加不遮擋中央地圖的功法面板，提供三組預設配置及目前技能按鈕；右側沿用四方向逐格移動控制。手機、平板仍可點選／長按靈獸，亦可點擊空白地格選擇技能中心或突進落點；地圖新增不蓋過角色的施法目標虛線框。
- 施法、切換配置和命中傷害由後端回覆及既有 SSE 同步。已裝備功法時不顯示普通攻擊；沒學到功法時保留基礎攻擊及原先的地圖移動。
- 單元測試涵蓋授權裝備、熟練／境界限制、直線、突進、劍陣、飛劍、擒拿、六層蓄勢、牆壁阻擋與操作防重；多人 API 測試涵蓋跨兩個伺服器的同步施法與三組配置。Chromium 雙玩家測試驗證點選技能、共享傷害、擊殺同步及戰中切換。
- **未完成範圍**：第 12 階段才接入原本的獨立答題／題庫預取／答對補體力；第 14 階段之後再完成守鑰靈獸、共享密鑰、傳送門與 Boss；第 19/20 階段才接入倒地救援與結算獎勵。這個版本仍使用暫時性的 100 點探索體力，不得冒充完整的正式副本。


## 第 12 階段：每位隊員獨立答題充能（已接入）

### 題目來源、品質與非回合制協作

- 每一位合作隊員使用自己的玩家身分、學習年級、原本儲存的「隨機／修習範圍／使用題庫」設定，各自取得與答完題目。絕對不以隊長的題目、答題次數、能力分數取代隊員自己的學習資料。
- `server.js` 的既有 `/api/generate-quiz` 加入 `quizMode:"dungeon"`，不另寫簡化型 AI 提示詞；沿用既有單選題生成、題型分工、修習範圍與適性細觀念、參考題目及獨立審核流程。若選「使用題庫」，則由原本有審核／解析的題庫檔或資料夾抽出四選一題目，不改由 AI 隨機替代。
- **隊伍一集結就背景備題**，不須先點擊充能。個人可用庫少於五題就再補至五個序號的緩衝區，一次最多兩路並行請求；若短時間內題目用盡則顯示「正在填充題庫中」，已取得的題目不因其他緩衝請求失敗而遺失。
- 題目以副本房間、集結時間、玩家 UID、修習範圍雜湊及個人答題序號隔離。A 上儲存待答題幹與答案，但在玩家作答前，瀏覽器只能看見四選項、題目及提示資料，不能拿到正解或解析。

### 批改、學習紀錄與跨資料庫入帳

- `dungeon-quiz-api.cjs` 在 Firebase **A** 對個人答題進行原子批改，寫入既有的作答紀錄、各科正確率、知識點足跡、`soloLearningV1`、適性學習和修煉獎勵；與一般問道試煉一樣，答案一送出即顯示完整正解及解析，使用者自己按「下一題」才會接題。
- **答對增加四點副本探索體力；答錯增加一點；個人體力上限 100。** 此規格沿用原本體力戰鬥的四／一獎勵，不代表正式掉落獎勵。伺服器先在 A 記錄已批改的帶序號憑據，再透過 `action:"quiz-credit"` 由 Firebase **C** 在同一個房間交易內核准與入帳；不接受前端提供的「答對」與獎勵數額。
- 由於 A/C 分屬不同 Firebase 專案，兩端無法同一筆交易；以「A 可重試的已批改結果」＋「C 嚴格遞增 `quizCreditSeq`」實現不重複領取。若 A 已批改而 C 補體力失敗，先保留原作答結果，之後可按「重試補充體力」依序補領，刷新和換裝置不會重複加體力。
- 批改完成後，解析畫面留在該玩家自己的學習紀錄，直到明確按下「下一題」才確認切換；只收合題目、返回戰場、重新連線或換裝置不會跳過已批改解析。回放同一題的答案不能再次增加學習分數或副本體力。
- 每位玩家獨立記錄答題、正確率與補充體力；其他玩家與 NPC 都照原本伺服器時鐘移動／攻擊。答題 UI 不會鎖住世界時鐘、停止 SSE 或強制全隊等待答完。
- 問道試煉的功法與輪次沒有更改；戰鬥中的手動攻擊和功法仍完全由副本既有伺服器決定，不允許答題請求夾帶技能傷害、位置、金幣或別人的體力。

### 驗證與剩餘項目

- `tests/dungeon-quiz.test.cjs`：5 題備題序號、個人範圍、學習統計、答案防洩漏、過期房間、解析確認、重送批改。
- `tests/dungeon-player-combat-api.test.cjs`：兩個 C 伺服器同時領取同一張 A 憑據，驗證最多入帳一次；跨玩家、偽造獎勵、非授權及跳號均遭拒絕；上限 100 的補充量會按實際可增加的值裁切。
- `scripts/test-dungeon-map-browser.cjs`：Chromium 兩人分別開啟獨立答題，檢查答對／答錯、完整解析、兩人生命與體力隔離、房間時鐘不暫停、多人同步及重送防重複；部署前透過 GitHub Actions 驗證。
- **後續階段仍未完成**：答題介面內的完整問道助手與超範圍回報工具（目前保留既有主頁工具，不假裝已在副本完成）、BOSS／守鑰靈獸、密鑰、傳送門、復活及副本結算。副本開始的 100 點探索體力仍沿用前期測試設定，後續平衡階段需要調整。

## 第 13 階段：即時功法表現、蓄勢金身與傷害一致性（已實作）

### 六層蓄勢：真正享有加成的技能才會變金色

- 龍象真身訣的「蓄勢」在多人副本內凝聚**6 層金身氣勁**；接下來六次成功施放的**體修攻擊**各消耗一層，該次體力費用減半、向上取整。重新施放「蓄勢」會重新凝聚六層，本身不消耗層數；不設技能冷卻，也不使用回合數。
- 畫面左側只有**當前真的受蓄勢加成的體修攻擊**才以金色漸層、光暈、✦ 符號與調整後的體力費用顯示。蓄勢本身不誤標金色；如果玩家切到劍修，劍招不享加成、不扣蓄勢；切回已裝備的體術，剩下的層數繼續有效。
- 技能面板明示「✦ 金身蓄勢 N/6 · 體術減耗」。成功施法後，伺服器回覆的 `lastSkill.focusEmpowered`、`focusBefore`、`focusCharges`、`cost` 決定提示與層數，**不是讓前端決定扣體力／扣層**。六層耗盡後，按鈕即恢復原本顏色及消耗，光環即時消失。

### 周身氣勁及共享視覺

- 持有有效蓄勢的玩家腳下有持續呼吸的金環、旋轉靈脈、四道上升金色粒子及剩餘層數標籤。效果與玩家的**實際伺服器座標**、副本地圖縮放／拖曳、多人重疊站位完全對齊；隊友也可透過 Firebase C 的房間同步看到該玩家的蓄勢，不只本人看得到。
- 金色光環以獨立、無點擊事件的 CSS 合成圖層呈現，保留中心透明，不會覆蓋角色標記，不新增整張地圖的高頻重繪。支援 `prefers-reduced-motion`：使用者要求減少動態效果時保留靜態光環。
- 縮圖中，正在蓄勢且未倒地的隊員也會有金色環線。每次成功施法只把伺服器計算的合法 `effectCells`（最多 72 格）經 SSE 傳給隊友；地面會短暫浮現**金色加成劍氣／拳勁痕跡**或一般青色攻擊痕跡。它們繪製在靈獸及玩家標記的下層，紅色危險攻擊預告仍保持可讀，不影響真實命中。
- 即時副本的技能說明移除舊戰棋「回合限制／結束回合」措辭；保留舊問道試煉的回合規則與說明，不做跨模式的破壞性修改。

### 後端一致性、驗收及界線

- 每次施法從 Firebase A 的**可信功法快照**重新計算已獲得功法等級帶來的副本攻擊力，避免升級後留在同一場副本卻繼續使用過期攻擊數值；技能基礎單擊與劍陣中心的傷害預覽由同一套功法計算式提供。
- `tests/dungeon-skill-combat.test.cjs` 追加六層耗盡、非體修技能不得消耗蓄勢、偽造金色／費用標誌無效、重新計算攻擊力、技能說明與基礎傷害預覽驗收。原來的幾何、撞壁、飛劍、多人同步與 NPC 戰場測試保留。
- `scripts/test-dungeon-map-browser.cjs` 以**兩個 Chromium 玩家**驗證「施放蓄勢 → 本人的體修技能變金色且減耗 → 兩人都看到角色金環 → 連續六次真實施招 → 層數歸零、金環消失、按鈕恢復一般顏色／費用」，並繼續執行原本移動、NPC 攻擊與答題補體力驗收。
- **目前未實作**：守鑰靈獸及密鑰、傳送門、Boss、倒地救援、正式戰鬥獎勵與平衡，均留待後續階段；此次增強的是已有功法的可靠性與視覺反饋，**不是**額外提高蓄勢技能的傷害。


## 第 14 階段：鎮鑰靈獸、全隊共享密鑰與首領傳送門（已實作）

### 新增的目標循環

1. 隊長正式集結時，伺服器使用與原本地圖相同的種子，將「鎮鑰玄甲獸」（守鑰靈獸）放在地圖最深處的主線尾端，若該格和既有靈獸重疊才退到前方最近的合法主線格。玩家無法自訂出生點、守護者位置與地圖種子。
2. **真正戰鬥**：守鑰靈獸在同一個伺服器權威 NPC 陣列中，起始 360 HP，每三個戰場秒 Tick 採取行動；玩家靠近時可經 BFS 追擊，使用有提前預警、可閃避的「鎮鑰裂地震波」（14 點副本生命傷害）。仍能由所有隊員的普通攻擊或已裝備功法造成傷害；一般問道試煉與舊團本規則不變。
3. **取得唯一共享密鑰**：當守鑰靈獸確實在 Firebase C 的攻擊／施法房間交易中被擊敗、移出權威敵人陣列時，同一筆交易把 `dungeonProgress.guardianStatus` 設為 `defeated`、`keyAcquired:true`、`portalStatus:'ready'`，記錄最後擊殺者與戰場 Tick。密鑰**自動歸屬整個隊伍**，不需要個人撿拾、不會因同時攻擊而發出第二把，也不能由前端直接要求領取。
4. **啟動傳送門**：玩家帶著全隊共享密鑰，走到地圖已預留的傳送陣格子或其上下左右一格，按「使用密鑰啟動傳送門」。`action:'activate-portal'` 會在 Firebase C 單一交易重新確認真實隊員、房間有效、戰場已開始、**密鑰已取得**、本人未倒地、距離合法，才把全隊共享 `portalStatus` 設為 `open`。不扣玩家探索體力，也不消耗或刪除共享密鑰；即使兩名隊員同時啟動，仍只提交一次進度，之後重送不會重複開門。
5. 開門後所有隊友透過原本的 SSE 得知「首領傳送門已啟動」，地圖標記切換為紫色的開門樣式。本階段只提供**首領戰的可信入口狀態**：不假裝已有傳送動畫、Boss 關卡、Boss 傷害或副本結算。正式進入首領戰留到下一階段。

### 地圖提示與多人互動

- 地圖上方以簡短任務進度即時切換「擊敗鎮鑰玄甲獸」、「已取得全隊共享密鑰」、「首領傳送門已啟動」。傳送門使用按鈕只在有密鑰後出現；未走到傳送陣附近會顯示原因並停用。
- 地圖和縮圖保留封印陣／守護區標記；當鑰匙已得時守護區改為完成標誌，傳送陣從灰色變青綠色（可啟動）再變紫色（已啟動）。守鑰靈獸用更大的專屬符號、獨立 HP 血條與資料面板呈現；其預告攻擊格仍畫在玩家和靈獸圖示的下層，不會蓋住人物。
- 所有進度來自 `publicRoom` 只包含安全進度欄位的 `dungeonProgress` 投影。畫面不能自行給鑰匙或開門；房間回到等待室、隊長解散或隊員離開並中斷此次探索時，交易清空目標進度。重新集結重新生出守護者，不保留上一場密鑰。
- **舊的進行中場次**如果沒有 `dungeonProgress`，不會從已擊殺的 NPC 紀錄憑空推斷鑰匙；需要結束舊場次再集結，才會啟用本階段的目標循環。

### 驗收與品質邊界

- `tests/dungeon-objectives.test.cjs`：800 個種子碼的守護者位置／唯一性、守護者真正攻擊預警、非守護者死亡不給密鑰、守護者死亡只給一次、距離／倒地／無密鑰不可開門、重送不變更狀態。
- `tests/dungeon-objectives-api.test.cjs`：兩個 Firebase C 伺服器實例同時擊敗守護者、僅一個共享密鑰、兩人同時啟動傳送門、非隊員和偽造前端資料無效、原已裝備功法擊殺、取消探索清除密鑰並可再集結。
- `scripts/test-dungeon-map-browser.cjs`：兩個 Chromium 玩家從原本的多人地圖、戰鬥、金身與答題走到守鑰任務，確認兩人都看見共享密鑰、靠近後才解鎖啟動鍵及開門後的全隊同步，重送不增加房間版本。
- 本階段**沒有**正式 Boss 關卡、復活系統、經驗／掉落結算與多人戰利品，也**沒有**額外的永久個人鑰匙道具；避免將「解鎖共享傳送門」誤當成「完成副本」。


## 第 15 階段：真正的多人即時 Boss 戰與獨立首領場景（已接入）

### 全隊從已啟動的傳送門進場

- 依循第 14 階段真實流程：先擊敗最深處的鎮鑰玄甲獸、全隊取得密鑰、由任一名活著的隊員靠近傳送陣並啟動。之後傳送陣旁才會開放「**全隊進入首領戰**」按鈕。已開門但離傳送陣太遠、沒有有效房間成員身分、角色已倒地或仍未取得密鑰，均不能偽造入場。
- `action:'enter-boss'` 由 Firebase C 的單一交易完成：驗證真實的密鑰與位置、建立唯一 `bossEncounter`、切換 `dungeonArena:'boss'`、實際移除上一場探索 NPC、一次將全隊傳送至**四個不同的首領戰出生點**。不能在進場請求夾帶角色位置、Boss HP、判定 Tick 或手動改變隊友數據；並行兩個伺服器請求只能進場一次。
- **保留**隊員既有生命、倒地狀態、探索體力、答題紀錄、功法配置、技能熟練與蓄勢剩餘層數；以原本房間的伺服器戰場時鐘繼續計算。個人飛劍的位置因跨場景而清空，避免飛劍從探索地圖穿越到不相干的戰場；隊伍房碼、成員與 Firebase C 房間本身完全不變。
- `get-map` 在探索階段回傳原來的可重現不規則地圖，進入 Boss 階段時則傳回由房間種子碼推導的另一張 **23×17 玄炎鎮殿**。兩台 Render 伺服器和四個玩家都會得到同一張圖；原有地圖放大、拖曳、縮圖、移動及問題充能仍然有效。SSE 報告場景切換後各裝置自動重新取得相應地圖、重設舊目標及鏡頭，不以同一張圖硬把角色瞬移至別的座標系。

### 真正的 2×2 首領與三段即時戰鬥

- 「**玄炎鎮殿獸**」是**同一隻** `boss-1`，HP 900，實際佔四個相鄰的 2×2 格子。移動、突進、飛劍落點、推進與普通攻擊都從伺服器檢查完整 2×2 佔地；任一身體格可成為合法命中位置，但一次完整擊中不會無故對同一 Boss 重複計算四份傷害。Boss 不能被翻摔、擊退到牆裡或被虛構為四隻敵人。
- Boss HP 依門檻自然變化：**第壹階段（高於 70%）**以「震地裂環」為主；**第貳階段（35～70%）**增加「玄甲衝鋒」的橫／直線衝擊；**第參階段（35% 以下）**加入「玄炎扇焰」的展開扇形火焰。三招都是從 Boss 的真實 2×2 身體格及地圖牆壁計算預告範圍，分別造成 11、13、16 點副本生命傷害；不以玩家答題或行動輪次推進。
- **時間與公平性**：全隊沿用每秒一次的權威戰場 Tick；Boss 以自己的下一次攻擊時間、攻擊計數與 HP 決定招式，所有預告格在攻擊前兩秒同步給隊友，移出範圍便可閃避。若伺服器與玩家失聯很久，恢復時只追上有限範圍且**不會補算任何玩家來不及看到的歷史傷害**；不同 Render instance 透過同一筆 C 交易避免重算攻擊與重複傷害。
- 玩家仍可隨時移動、普通攻擊、施放功法或獨立答題補體力，戰場時鐘不會因有人答題或關閉視窗而停下。Boss 造成的傷害只寫入該名隊員的副本生命，並沿用前期原有倒地規則。蓄勢的金色六次加成仍保留；其他隊友可透過 SSE 看到金色氣勁與實際 Boss 血量。
- Boss 真實死亡後，`bossEncounter.status` 設為 `defeated`，記錄最後擊殺者與 Tick。重送最後攻擊、重複技能操作或多台伺服器同時擊殺，不會復活 Boss、重複記錄擊殺或額外扣體力。

### 戰鬥畫面與明確保留的下一階段

- 首領場景有自己的地圖標題、資料窗和縮圖；Boss 以兩格寬的獨立玄甲標記、人物圖示下層的大型身軀、即時血條與浮動標籤呈現。頂部顯示 **900/900 Boss 血量、目前第壹／貳／參階段**，並在危險招式發動時顯示明確預警。隊員在小螢幕仍能看到自己的移動、體力與功法，不以滿版紅色攻擊區遮住角色。
- 隊伍大廳同樣顯示已進入 Boss 戰或已完成 Boss 擊殺，不再錯誤宣稱 Boss 尚未開放；所有畫面以同一個 C 房間狀態為準。
- **第 15 階段不發放正式 Boss 掉落、永久角色經驗、功法熟練獎勵或副本結算獎品**。這些會與倒地救援、出場／結算、團隊獎勵一起在後續階段以獨立可驗證交易完成，不可因畫面顯示「已擊敗」就先發放虛構的獎品。

## 第 16 階段：協力救援、凝神復起與 Boss 個人勝利結算（已接入）

### 非回合制救援與防止整隊永久卡死

- 在探索與 Boss 戰期間，倒地隊員會由房間 SSE 即時顯示；**任何仍站立的隊員**可以走到對方同一格／相鄰上下左右一格，按「✚ 救援」，由 Firebase **C** 的一筆房間交易再次驗證身分、距離、目標確實倒地、雙方目前生命與體力，**消耗救援者 8 點探索體力，將隊友恢復至 40/100 HP**。每個隊員一場最多接受 **2 次隊友救援**，避免無成本無限續命。使用者不必放棄當前技能配置、返回等待室或等待敵人回合。
- 若全隊均倒地，任一倒地修士還可以在獨立答題充能後，按「✦ 凝神復起」，**消耗自己 25 點探索體力，恢復 25/100 HP；一場只能使用一次**。自己仍活著時不能使用，已用過則需由隊友救助。這不是偷偷提高副本攻擊力或角色原本修為；是避免所有隊友都倒地後再也無法移動的最後手段。
- `action:'rescue'` 只接受 `roomId`、`targetUid` 和自己遞增的 `seq`。所有實際體力、救援數、生命與倒地狀態由**後端權威的 C 交易**計算，並且先追上已到的敵方攻擊節拍，再決定能否救援。玩家端不能自行指定復活血量、救援距離、代價或替別人送出操作。
- 每位玩家有獨立 `rescueSeq` 和 `lastRescue`，同一成功操作（包含跨 Render 伺服器重試）只會入帳一次；隊伍不會因不同裝置爭搶最後一次救援而重複扣費。所有隊友即時看到 HP 從 0 恢復，隊友名單隨之更新。重新集結／結束此次探索會清除救援次數與序號，不把副本生命寫入永久角色資料。
- Boss 被擊敗後不再需要戰鬥救援；救援只在進行中的副本時可用，且不暫停原本的即時戰鬥時鐘。答題畫面仍然可以獨立使用，學習分數與錯題訂正規則不因救援而變更。

### 正式個人獎勵：靈石與修為

- 真正擊敗玄炎鎮殿獸後，所有參戰隊員的地圖上會顯示共用「全隊勝利」面板；每人可以獨立按下「**領取 120 靈石 ＋ 3 修為**」。這次**實際寫入**原本 Firebase **A** 的 `users/{uid}.stats.gold`、`stats.totalScore` 並增加個人 `stats.dungeonBossWins` 計數，不是只在畫面顯示假獎勵。
- `action:'claim-boss-reward'` 的唯一憑據是 Firebase **C** 可信房間：仍有效的同場 `dungeonArena:'boss'`、守鑰靈獸已死、共享密鑰／傳送門已開、Boss 已被伺服器擊殺、敵人清單不再包含該 Boss、擊殺者屬於實際成員、進場與擊敗 Tick 合法。必須是**自己的有效 Firebase A 身分**且屬於這場實際隊員，才能領自己的一份；不能透過請求指定修為、靈石、隊友 UID 或傳入假的 Boss HP。
- 一份獎勵會在 Firebase **A 單一交易**內同步更新個人角色財產與獨立 `dungeonVictoryClaims` 收據；收據 ID 為帶房間 ID、**集結時間戳**與本人 UID 的 SHA-256。多個伺服器／裝置同時領取或重新送出請求，只能成功增加一次靈石和修為；之後返回 `duplicate`，不讀取舊收據的過時財產快照覆蓋目前餘額。
- 不額外發放已取消的材料、不私自修改舊團本券或舊團本的每日獎勵；修為仍計入既有境界門檻。這筆正式結算**需要在有效副本場次中按下領取**，勝利面板明確提醒離開隊伍前完成入帳；場次逾期或離隊後目前不會提供跨場次補領功能。
- A 與 C 是**不同 Firebase 專案**：Boss 勝利先在 C 確定，個人領取再在 A 完成原子入帳。不能宣稱兩個資料庫構成單一原子交易；若 A 暫時無法連線，勝利仍保存在目前 C 房間，玩家可重試，不會因領取失敗就把獎勵標成已領。

### 新增畫面與驗收

- 同一個合作副本頁面中，隊友倒地後會依位置、剩餘體力及上限顯示可操作的救援按鈕或不能救援原因。自己倒地時顯示「凝神復起」，可繼續答題補足體力。救援成功後立即更新隊友生命與個人探索體力，並透過原本 SSE 同步，不新增回合制、按兩次充能或技能冷卻。
- Boss 真正死亡時畫面上方顯示精簡的勝利與個人獎勵面板；按下領取後呈現「已領取」或「先前已領取」。手機直式與橫式維持不遮蔽大部分戰場的版面。
- `tests/dungeon-rescue-reward.test.cjs`：完整驗證倒地與合法相鄰救援、HP/體力數值、2 次隊友援救及 1 次自救、防作弊指令、兩伺服器同時救援與重送、Boss 偽造勝利不可領取、兩名隊員同時領取、A 收據唯一性與原有角色資料實際增值。

- 本階段**還沒有**擴充永久寶物掉落、隨機裝備、跨場次補領、退出副本獨立結算頁和大型數值平衡；避免與已移除的材料／抽裝備功能產生矛盾。
